## 3. 当前数据定位

CARE 数据用于支持：

1. 验证系统能否识别有标签异常事件。
2. 分析事件前可解释的状态变化。
3. 为风险分级和维护触发条件提供实验依据。
4. 为数据库、API 和数字孪生提供可追溯的状态数据。

CARE 不直接提供项目所需的全部人员配置、维修工时、维修成本和天气窗口。这些参数在 v0.1 中必须标记为 `SIMULATED` 或 `ASSUMED`。

## 4. 数据质量边界

- 多个风场的 Min、Max、Std 统计量存在已知质量问题，不能无差别输入模型。
- 第一版优先从完成质量检查的 Avg 信号中选取建模字段。
- Wind Farm B 原则上以 Avg 信号为主。
- Wind Farm A 的 Pitch Angle 可能存在角度环绕问题，使用前需专门处理。
- Wind Farm C 的不同匿名传感器污染程度不同，需逐字段筛选。
- Version 6 修正了部分单位和事件信息，项目不得混用旧版本定义。
- 训练、验证与测试必须按时间逻辑划分，避免使用事件后的信息预测事件前状态。

## 5. Event 51 MVP 证据

Event 51 已完成三项交叉核验：

- Wind Farm A 的 `event_info.csv`：`asset=21`，`event_id=51`，标签为 `anomaly`。
- 事件区间：`2023-10-06 01:30:00` 至 `2023-10-17 16:10:00`，对应 `event_start_id=52331`、`event_end_id=54003`。
- 数据文件 `Wind Farm A/datasets/51.csv` 存在，`asset_id` 全部为 21，共 54,436 条 10 分钟记录；其中 `train=52,043`、`prediction=2,393`，事件区间包含 1,673 条记录。

官方事件描述为 `Gearbox bearings damaged`。因此 Event 51 可作为 v0.1 主案例，场景标记为 `ONSHORE`。系统对象仍使用 `WT02_COMPONENT_01`，直到全队完成 CARE 原始对象到系统对象的正式映射记录。

Event 51 文件关键质量统计：`sensor_11_avg` 无缺失，均值 51.555、范围 23.000-69.000；`sensor_12_avg` 无缺失，均值 47.564、范围 25.000-61.000；`sensor_13_avg` 无缺失，范围 20.000-205.000；`sensor_14_avg` 有 1 条缺失，不能在未处理前直接作为模型输入。

## 6. 标识与命名规则

- 匿名传感器只能依据 README、`feature_description.csv`、论文或其他可追溯资料解释。
- 映射确认前不把 `sensor_XX` 命名为具体温度、振动或部件信号。
- 映射确认前使用 `WT02_COMPONENT_01`，并保持 `mapping_status=UNVERIFIED`。
- Event 51 是重点核验候选；在事件、字段和实际时序交叉验证前，不把它作为已经完成的核心案例。

## 7. 数据真实性分类

| 类型 | 定义 | 本项目示例 |
| --- | --- | --- |
| `REAL` | 可追溯的真实公开数据 | CARE 原始 SCADA、官方事件信息 |
| `DERIVED` | 由已声明来源计算的结果 | 清洗数据、特征、异常分数、风险评分 |
| `SIMULATED` | 为系统演示构造的条件或结果 | 天气变化、人员变化、模拟维护结果 |
| `ASSUMED` | 缺少真实参数时设定的规则 | 风险阈值、人员单位 |
| `REFERENCE` | 来自论文、标准或数据说明的信息 | 风场类型、资料中的定义 |

## 8. GitHub 存储规则

- 不提交完整 5.5 GB 数据包。
- 原始数据保持只读，不手工覆盖。
- 仓库只保存数据来源、元数据、处理脚本和必要的小型复现实验样本。
- 不提交 Token、密码、个人隐私或受限数据。
- 每次实验记录数据版本、代码版本、模型版本、参数和输入样本。
